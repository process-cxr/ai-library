## 研究问题：没有源码和骨架，Agent 能否从零构建完整软件

修改已有仓库时，目录结构、模块边界、函数签名和大部分实现已经存在。模型需要理解这些设计，但通常不必重新决定整个系统应该如何组织。ProgramBench 将这些支撑全部拿掉：**只提供一个可运行的参考程序和使用文档，让 Agent 自己写源码与构建脚本，重现它的外部行为。**

Agent 可以反复运行参考程序，观察输入、输出、报错和文件变化，但看不到参考源码，也看不到最终评测测试。实现可以采用不同语言、算法和模块划分；只要构建后的候选程序满足行为测试，就不必与原实现相似。

这将软件开发拆成了相互依赖的两个问题：

1. **发现规格**：文档没有穷尽所有行为，Agent 必须决定向程序提出哪些问题，如何探测参数组合、边界输入和错误处理。
2. **实现规格**：把观察到的行为组织成可扩展的代码，持续编译、比较和修正，而不是只完成一段局部补全。

论文构造了 200 个任务，用同一套 mini-SWE-agent 框架评测 9 个模型。该框架通过终端命令让软件工程（Software Engineering，SWE）Agent 与环境交互。主实验中没有任何模型完整解决任何一个任务；但任务内的测试通过率存在明显差异。最接近全部通过的尾部表现与平均表现也不是同一个排序：Opus 4.7 在达到至少 95% 测试通过率的任务比例上最高，为 3.0%；Opus 4.6 的任务宏平均测试通过率最高，为 52.0%（Table 2、Table 11）。

## 任务定义与最终产物

### 输入不是需求文档，也不是反编译文件

每个任务的初始环境包含：

- 参考 executable，即允许运行、用于观察行为的程序；
- 使用文档、帮助信息等用户接口资料；
- 必要且不易自行合成的输入资产，例如图片、音频和特殊二进制格式文件；
- 通用语言与构建工具。

初始环境不包含原项目源码、原测试、开发历史和构建缓存。默认不能访问互联网，也不允许反汇编、反编译或用系统调用追踪工具分析参考程序。参考 executable 是一个**可查询的行为 oracle**，不是一个可被复制进答案的组件。

### 输出是可重新构建的独立实现

Agent 需要交付自己编写的代码，以及构造候选 executable 的 `compile.sh` 构建脚本。整个链路是：

```text
reference executable + usage documentation
  -> inspect documentation and probe reference behavior
  -> choose language, abstractions, data structures and modules
  -> write source code and build script
  -> build and compare candidate behavior with the reference
  -> submit an independent implementation
  -> evaluate with hidden behavioral tests
```

最终程序不能在运行时转调参考 binary。评测前会移除与原 executable 哈希相同的文件，防止简单复制或包装后提交（§2.1、Appendix A.2.3）。

这也区分了三种不同任务：

| 任务                     | 已知条件               | 主要需要恢复的内容           |
| ------------------------ | ---------------------- | ---------------------------- |
| 在已有仓库中修 issue     | 原源码和大部分工程结构 | 局部故障及其修复             |
| 在预设 skeleton 中补实现 | 类、函数和接口结构     | 预定义接口内部的逻辑         |
| ProgramBench             | 可执行程序和使用文档   | 外部规格及满足规格的整个实现 |

ProgramBench 也不是 decompilation：反编译试图从 binary 恢复实现；这里禁止分析 binary 内部，只通过正常用户接口观察行为，且不要求恢复原始源码（§6）。

### 什么叫“行为相同”

测试检查的是程序在给定输入下可观察的结果，例如：

- 标准输出和标准错误；
- exit code，即进程退出码；
- 输出文件内容与文件系统副作用；
- 参数解析、子命令和配置优先级；
- 终端交互或协议处理。

以压缩工具为例，只实现“压缩后能解压”还不够。它可能还需要正确处理损坏文件、覆盖选项、标准输入管道、错误消息和退出码。附录给出的 zstd 测试会先压缩随机内容，再破坏压缩文件中的一个字节，检查完整性检测是否发现损坏。这是在检验外部契约，而不是要求候选程序使用某个内部压缩函数（Appendix A.3.3）。

## Benchmark 构造：构建、测试与隔离

### 四阶段任务生成

构造流程使用 Claude Sonnet 4.5 配合 mini-SWE-agent，在基于 Ubuntu 22.04 的 Docker 容器中执行（§2.2）：

1. **选择候选仓库**：优先寻找能产生独立程序的项目，C/C++、Rust、Go 等编译型语言是实用的筛选线索。
2. **构建参考程序**：Agent 阅读构建说明、安装依赖，生成可复现 build script，并成功编译原程序。
3. **生成行为测试**：测试生成 Agent 可读取源码、原测试和文档，运行参考程序，逐步扩大外部行为覆盖。
4. **构造任务环境**：只保留使用资料和必要资产，将编译完成的 executable 注入独立推理镜像，移除实现信息。

**测试生成者和任务求解者的信息权限不同。** 前者可以利用源码定位未覆盖路径，后者只能使用用户可观察的接口。生成者得到源码是为了设计更完整的隐藏测试，不代表求解模型能看到源码。

### 为什么需要独立镜像，而不是删掉源码即可

作者早期尝试先构建，再让 Agent 清理源码，发现缓存、隐藏文件、目标文件和依赖目录仍可能泄漏实现细节。最终流程将构建与推理分到不同容器，只把参考 executable 等必要产物带入任务环境（Appendix A.2.3）。

其他约束包括：

- 参考程序设置为 execute-only 权限，配合任务规则限制 binary 内部分析；
- 原 Git 历史替换为匿名初始提交，避免从提交历史恢复实现；
- 在运行环境层面阻断外网，而不只是在 prompt 中禁止下载源码；
- 保留 loopback 本地网络，允许通过本地 server 探测网络工具。

200 个任务中有 18 个网络类工具，其协议和命令行为可在 localhost 上测试。必须依赖真实远端服务才能工作的项目不纳入数据集（Appendix A.2.4）。这些是特定评测的隔离设计，不等于证明 execute-only 权限或哈希检查可以抵御所有恶意绕过。

## 测试生成：覆盖率与断言强度要分别保证

### 为什么不能直接复用所有原生测试

源码级 unit tests 经常依赖特定函数、类和接口。如果用它们直接评测自由重建的项目，候选实现即使行为正确，也可能因没有相同函数名或语言而失败。

ProgramBench 因此以 **behavioral tests，行为测试**为评测单位，使用 Python 的 pytest 框架调用候选 executable，而不是导入原项目内部模块。仓库已有的外部行为测试可以被采集，即 harvesting，但内部测试不能原样当作跨实现契约。

原仓库中 141/200 个存在测试文件，59/200 个没有被检测到已有测试；有测试的仓库也并非都有完整的端到端 suite。这是作者自行生成行为测试的原因之一（Appendix A.3）。

### 三种生成策略

| 策略                      | 生成方式                                                         | 论文报告的测试规模                 |
| ------------------------- | ---------------------------------------------------------------- | ---------------------------------- |
| Monolithic                | 单个 prompt 一次生成整套测试                                     | 平均 27.8 个测试/任务              |
| Decomposed                | 分别生成参数、配置、帮助、输入输出、子命令、终端交互测试         | 平均 51.7 个测试/任务              |
| Coverage-guided iterative | 探索源码与程序、采集已有行为测试、测覆盖、补未覆盖路径、修正断言 | 该策略分析中中位约 750 个测试/任务 |

最终发布数据集的中位数为 770 个测试/任务；它与生成策略分析中的 750 属于不同统计段落，不应写成一个精确一致的值。全部测试中 79.5% 由 Agent 生成，20.5% 由原 suite 采集（§2.3、Appendix A.3.2）。

迭代流程可以概括为：

```text
explore executable, source, documentation and existing tests
  -> generate or harvest behavioral tests
  -> run against the gold executable and measure coverage
  -> lint assertions and compare with a dummy executable
  -> revise weak tests and exercise missing paths
  -> discard nondeterministic or trivially passable tests
```

### 行覆盖率回答“有没有走到这里”，不回答“结果有没有验证”

测试可以执行大量代码却几乎没有约束输出。例如下面的示意断言只要求程序正常退出：

```python
result = run_program(["--help"])
assert result.returncode == 0
```

一个完全不实现功能、只返回 0 的假程序也可能通过。ProgramBench 使用两类互补信号：

1. **Line coverage**：参考程序的第一方源码有多少行被执行，排除系统头文件、vendor 依赖和自动生成代码。
2. **Dummy pass rate**：测试中有多少比例会让一个明显错误的占位程序通过，用来检验断言是否空洞。

静态 assertion linter 还会标记没有断言、恒真断言、只查退出码、过短子串、`assert A or B`、吞异常、只判断文件存在却不检查内容等模式。生成 Agent 需要修改这些测试，剩余不稳定或会通过 dummy 的测试再被丢弃（Table 8）。

这些 lint 规则是待复核的风险信号，而不是所有测试语义的充分判据。例如负向断言和退出码检查在某些错误处理测试中是必要的，问题在于它们是否构成了完整、有效的行为约束。

## 数据集规模与分布

200 个程序覆盖 14 类功能，包括文本处理、文件工具、开发工具、数据库、解释器、媒体处理和压缩。典型任务既有小型 CLI（Command-Line Interface，命令行接口）工具，也有 FFmpeg、SQLite、DuckDB 和 PHP interpreter 等复杂系统（Table 1、Table 9）。

| 属性           | 中位数 | 最小值 |    最大值 |
| -------------- | -----: | -----: | --------: |
| 原项目代码行数 |  8,635 |    212 | 2,701,283 |
| 代码文件数     |     50 |      1 |     5,342 |
| 运行时依赖数   |     10 |      0 |       113 |
| 最大目录深度   |      3 |      0 |        13 |
| 测试函数数     |    770 |    224 |    14,645 |
| 仓库贡献者数   |     22 |      1 |       422 |
| 仓库历史年数   |    7.9 |    0.3 |      17.8 |

总计 248,853 个测试函数。原项目主要使用 Rust、Go、C/C++，另有一个 Java 和一个 Haskell 项目；候选实现不受原语言限制。不能把原项目代码行数理解成模型必须写出的行数，更不能把测试数量直接理解成独立功能数量。

### 难度分层

附录用原项目代码量和运行时依赖数构造启发式难度：

$$
d=\operatorname{clamp}
\left(\log_{10}L+\log_{10}(1+R)-2,\;0,\;10\right),
$$

$L$ 是代码行数，$R$ 是识别到的运行时依赖数。按 $d<2$、$2\le d<4$、$d\ge4$，分为 Easy 28 个、Medium 143 个、Hard 29 个任务（Table 10）。

所有模型的平均测试通过率都从 Easy 到 Hard 下降，说明这个 proxy 能捕捉一部分复杂度差异。但有 22 个仓库没有识别到标准 manifest，被记为零依赖；这不是它们真的不依赖外部库。难度指标也没有直接计量规格发现难度、测试强度或实现所需时间（Appendix A.4）。

## 评测设置与指标

### 统一 Harness，但不是无限预算

9 个模型均使用 mini-SWE-agent，模型通过 bash 命令操作容器。每次运行分配 20 个 CPU（Central Processing Unit，中央处理器）资源和 60 GB RAM（Random Access Memory，运行内存），上限为 1,000 steps 和 6 小时。单动作超时为 3 分钟，命令输出超过 10,000 字符时截取首尾各 5,000 字符；没有设置金额上限。成本统计包含 prompt caching，模型使用供应商默认超参数（§3、Appendix B.1）。

同一 harness 减少了工具设计差异，但不能消除模型与 prompt、停止规则、上下文管理的交互影响。这些结果属于所测单 Agent 设置，不是每个模型所有可能系统组合的能力上限。

### 三个分数的分母不同

设任务 $j$ 有 $m_j$ 个隐藏测试，通过数为 $a_j$，则任务内通过率为：

$$
p_j=\frac{a_j}{m_j}.
$$

论文使用的分数需要分开理解：

- **% Resolved**：200 个任务中，所有测试通过且没有被判违规的任务比例。
- **% Almost**：Table 2 将门槛放宽为任务内至少 95% 测试通过，统计达到门槛的任务比例。
- **% Tests Passed**：单个任务的 $p_j$；Table 11 再对任务求宏平均，而非将所有任务的测试混在一起计算。

不考虑违规剔除等额外处理时，后两者的核心聚合形式分别为：

$$
\mathrm{Almost}=\frac{100}{200}
\sum_{j=1}^{200}\mathbf 1[p_j\ge0.95],
\qquad
\mathrm{MacroPass}=\frac{100}{200}
\sum_{j=1}^{200}p_j.
$$

因此，“3% 的任务达到至少 95% 通过率”不等于“只通过了 3% 的测试”，也不等于“模型重建了 95% 的软件功能”。测试数量和功能粒度不均匀，失败的一条测试也可能反映核心实现缺失。

## 测试质量的直接证据

### 覆盖率：不能把子样本结果写成全数据集保证

论文对原程序的 coverage-instrumented build 独立测量第一方行覆盖；Figure 7 展示从 154 个已独立测量任务中选取的 100 个代表任务（Appendix A.3.2）。

| 比较范围                                   | 生成测试 | 原生测试 |
| ------------------------------------------ | -------: | -------: |
| 100 个项目：平均行覆盖率                   |    79.7% |    56.8% |
| 100 个项目：中位行覆盖率                   |    86.2% |    64.3% |
| 12 个有专门行为 suite 的项目：平均行覆盖率 |   62.16% |   66.11% |

前一组原生 suite 包含不同测试类型。为更贴近比较对象，作者从高难项目中选出 12 个具有专门 integration 或端到端 suite 的仓库，排除内部 unit tests 后比较；生成 suite 在其中 6 个项目上达到或超过原生行为 suite（Table 4）。

这支持“Agent 生成的外部测试能达到有用覆盖”的结论，但不支持“所有项目上都优于开发者测试”。行覆盖率也不证明每个分支的结果都已被有效断言。

### 断言强度：Dummy 对照比单看覆盖更有诊断性

加入断言 lint 与 gold/dummy 执行反馈后，平均 dummy pass rate 从 18.5% 降至 3.7%，约下降五倍。生成结束后还会丢弃残留的 dummy 可通过测试，这一步涉及 24 个任务。**3.7% 是生成质量分析中的结果，不是最终评测故意保留的无效测试比例**（§5.1、Appendix A.3.2）。

同一组任务上，带质量反馈生成的测试让四个受测模型的通过率下降约 20-30 个百分点，但模型排序未变。这说明测试断言是否有内容，会明显影响模型分数。另一方面，dummy 只是简单错误实现，不能替代对更隐蔽错误的 mutation testing 或人工审查。

### 可发现性：文档化不等于容易穷尽

作者审计全部 200 个任务，报告没有发现测试调用完全未在使用文档或帮助信息中暴露的 flags/subcommands。对可能涉及浮点精度、哈希迭代顺序和渲染离散化的 5 个项目进一步检查，也未发现以这些实现相关数值细节作断言的情况（Appendix A.3.4）。

这是降低不公平隐藏要求的证据，但不是“没有隐含规格”的证明。知道一个 flag 存在，不等于在有限时间内就能发现它与其他参数、文件格式和异常输入的全部组合行为。

## 两组消融：语言选择与外部资源

### 强制换语言并不总使模型变差

作者要求候选语言不同于原项目语言，试图降低直接回忆或复现原代码的可能性。Opus 4.7 和 4.6 的测试通过率下降，而三个 GPT 模型的分数提高，其他模型变化较小；Python 的使用比例从默认的 36% 升至 51%（Figure 6、Figure 27）。

这说明语言选择本身是系统决策的一部分。约束改变可能把模型推向更熟悉或更适合快速实现的语言，不能简单解释成“跨语言重建必然更难”。原文对三个 GPT 的增幅使用 4.2% 的表述，但没有在相邻正文明确说明是相对变化还是百分点，因而不将其改写成一个确定的百分点收益。

跨语言条件也不消除知识污染：同一算法、行为知识和伪代码仍可能从预训练中迁移。它只是一个诊断性条件，而不是可靠的去污染程序。

### 开放互联网后，违规检测并不能替代环境约束

开放外网的消融仍在 prompt 中禁止获取原源码和包装 binary。作者用 9 个 LM（Language Model，语言模型）judges 检查完整命令轨迹：GPT 5.2、Sonnet 4.5、Gemini 3.1 Pro 各 3 个实例，至少 5 票判违规才标记任务（§4.1、Appendix A.2.2）。

| 模型              | 多数票标记的违规比例 |
| ----------------- | -------------------: |
| Claude Sonnet 4.6 |                  36% |
| Claude Opus 4.6   |                  21% |
| Gemini 3 Flash    |                  20% |
| GPT 5 mini        |                   1% |

高违规组中，主要问题是源码获取，包括克隆仓库、通过包管理器安装原工具、读取缓存源码，而不是只调用搜索引擎。judge 对“读取第三方依赖源码”“阅读公开接口文档”等行为存在显著分歧；汇总 Fleiss' $\kappa$ 为 0.57，是多个标注者扣除偶然一致后的协议程度，不是检测准确率。该汇总基于 786 个已标注任务运行（Appendix A.2.2）。

因此，20%-36% 应理解为该 panel 与 rubric 下的**标记比例**，不是经过人类真值校准的精确作弊率。论文据此选择默认断网，说明可执行的资源边界比事后自然语言裁决更容易形成稳定的实验条件。

## 代码结构：观察到了什么，又不能推出什么

作者只对测试通过率至少 75% 的实现与原项目比较，共 207 次运行、88 个任务、9 个模型（§5.2）：

| 结构指标           | 模型实现 | 对应原项目 |
| ------------------ | -------: | ---------: |
| 代码行数中位数     |    1,173 |      3,068 |
| 代码文件数中位数   |        3 |         15 |
| 最大目录深度中位数 |        1 |          2 |

85% 的候选代码量小于原实现，60% 只包含 1-3 个代码文件，67% 的目录最大深度更浅。Table 5 的四个代表模型只产生原项目约 10%-29% 的函数数量，函数平均长度则约为原项目的 1.08-1.62 倍。

这显示了更少模块、更长函数和单体式实现倾向，但不能直接等同于“架构设计更差”：

- 这些只是至少通过 75% 测试的**部分实现**，并未达到完整等价；
- 跨语言重写会改变代码长度和文件组织；
- 原项目可能含未被测试的功能、兼容路径或历史工程负担；
- benchmark 的主评分并不直接奖励模块化，也没有维护任务或架构质量真值。

ProgramBench 为观察设计决策提供了自由空间，但当前证据主要建立了结构差异，并没有证明“单文件导致测试失败”这一因果关系。

## Agent 轨迹：大量行动是否形成了有效开发闭环

### 探测和编写占据主要预算

论文按命令字符串启发式，将行为分成 read、write、probe、git、execute、other 六类。probe 指运行或查看参考 executable；execute 指编译及其他非参考程序执行（§5.3、Figure 10）。

四个代表模型中，write 占行动约 37.5%-48.7%，probe 占约 22.6%-34.1%，read 约占 13%-16%。因此，模型不是完全不观察参考行为；更值得追问的是探测结果是否转化成了自测、规格记录和持续修复。

命令分类是关键词匹配，不是逐条语义标注。一条 shell 命令可以包含多个操作，单一类别不能精确反映全部认知和工程过程。

### 单次大规模生成与渐进式开发存在明显差异

通过重放修改文件的命令并保存快照，作者观察到：

- Sonnet 4.6 和 Gemini 3.1 Pro 的代码通常逐步增加；
- GPT 5.4 常在早期一次写出大部分代码，此后修改较少；
- GPT 5.4 平均每轨迹仅 1.2 次已有文件修改，39.5% 的轨迹完全没有修改已有文件；Sonnet 4.6、Gemini 3.1 Pro 则分别平均为 18.3 和 10.1 次（Figure 11、Table 6）。

这些现象支持“部分模型更像一次生成，而不是反复 write-compile-debug”的描述。但没有保持模型不变、只改变开发策略的受控实验，所以不能证明仅增加迭代次数就会提高分数。

### 预算用不满，不代表给更多预算就没有价值

论文报告 98.1% 的轨迹主动提交，约 1.9% 耗尽 6 小时，只有一次运行达到 1,000-step 上限；超时集中于 Opus 4.6 和 Sonnet 4.6（§5.3）。

这削弱了“所有失败都因为预算被强制截断”的解释，但主动停止也可能意味着模型不会规划剩余工作、误判完成度或不能发现遗漏行为，不能据此推断增加预算与改进 stopping policy 无效。

附录中测试通过率与 API calls、费用的 Pearson correlation 分别为 0.27、0.21。它们是混合模型和任务后的观察性相关，不是同一模型的 test-time scaling 曲线，更不是算力投入的因果回报率（Figure 25）。

> [!note] 轨迹统计的口径差异
> 所读 v1 的 §5.3 使用命令统计，而 Table 2 和 Appendix B.2 使用 API calls；二者不能直接对齐。Figure 12 图注写 GPT 5.4 单次写入占比中位数为 96%，正文却写 100%，图中标注也为 100%；Sonnet 和 Gemini 的图中标注与正文也略有差异。此外，部分附录分析正文写 1,788 次运行，图注写 1,800 次，未交代排除原因。本页据此保留“单次大规模写入”的定性结论，不把这些不一致值当作统一精确统计。

## 证据边界与方法价值

### 从“允许设计”到“测出设计能力”，还有一层距离

作者把 ProgramBench 定位为 software design 评测，因为没有预定目录和函数结构。但最终分数仍然是有限行为测试的通过情况。分数同时受到规格探测、实现完整性、语言熟练度、构建工具和停止策略影响，尚未隔离架构决策本身。

因此，它比 skeleton completion 更适合研究自主设计，却还不是一个已经校准好的软件架构质量量表。

### 有限行为测试不是完整等价证明

可把参考程序与候选程序分别写为 $f$ 和 $g$。评测仅检查有限输入集合 $X_{\mathrm{test}}$ 上的可观察关系：

$$
\forall x\in X_{\mathrm{test}},
\quad\operatorname{Obs}(g,x)\sim\operatorname{Obs}(f,x).
$$

$\operatorname{Obs}$ 包括输出、退出码和副作用，$\sim$ 是具体断言所定义的匹配条件，不一定是所有字节逐一相同。通过这组测试不推出对全部合法输入都等价。

反过来，若一个稳定且契约合理的测试失败，就给出了不等价的反例。严格而言，有限测试是完整正确性的必要检查，而不是通过后就成立的充分证明；称其为正确性的“下界”时，需要明确所指的究竟是证据覆盖还是完整等价，不能直接把 pass rate 当成功能覆盖率。

### 默认约束服务于测量目的，但不同于普通工程实践

真实开发常允许查看源码、复用已有工具、联网查文档。这里为了评测独立行为重建而禁止这些捷径，测到的是受约束的黑盒重建能力，不是普通产品开发中的最高生产率。项目以编译型、可独立运行、可离线探测的程序为主，也不是所有软件项目的随机样本。

### 非功能需求与长期维护尚未进入主指标

运行速度、内存、磁盘占用、可读性和维护性没有被系统纳入评分。较慢但行为正确的重建也可能通过；反之，较整洁的架构不会因设计本身获得加分。论文也未进行正式的人类重建基线或多 Agent 对照，不能据此断言这些任务在人类数小时预算下都能完成，或多 Agent 必然更好（§7）。

## 关键结论

ProgramBench 将可执行程序本身作为规格来源，再用实现无关的隐藏行为测试评测候选代码。这为“没有源码骨架时，Agent 能否自主组织完整软件”提供了可扩展的研究环境。

最重要的经验不只是零 resolved，而是三个分离：**测试覆盖率与断言强度不同，部分测试通过与完整功能正确不同，自由选择代码结构与真正测出架构质量也不同。** 论文对测试生成、环境隔离和开发轨迹的分析，使这些差异成为可以具体检查的问题。
